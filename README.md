# Orquestrador

Self-hosted CI/CD orchestrator written in Python, a simplified version of tools such as GitHub Actions and Jenkins. Pipelines are defined in YAML and executed locally or (in upcoming phases) triggered by GitHub/GitLab webhooks, running inside Docker containers.

> Portfolio project built incrementally, phase by phase.

## Installation

Requires Python 3.11+.

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
```

## CLI Usage

```bash
# Validate the pipeline and show the execution order
orquestrador validate examples/hello.yml

# Run locally, simulating a push to main
orquestrador run examples/hello.yml --event push --branch main

# Extra variables, parallel jobs and JSON report
orquestrador run pipeline.yml -e VERSION=1.2.3 --parallel 4 --report result.json
```

Exit codes: `0` success, `1` failure, `2` invalid pipeline, `130` cancelled (Ctrl+C).

## Docker Container Execution

```bash
orquestrador run examples/docker.yml --executor docker            # CLI
ORQ_EXECUTOR=docker orquestrador serve                            # server
```

Each **job** gets its own container, created from `image` (from the job, pipeline or `ORQ_DOCKER_DEFAULT_IMAGE`), with the workspace mounted at `/workspace`. Steps run via `docker exec` in the same container, so files generated by one step remain available to subsequent steps. The container is removed when the job finishes.

```yaml
image: python:3.11-slim        # default for all jobs
jobs:
  test:
    image: python:3.12          # overrides
    env: { PYTHONUNBUFFERED: "1" }
    volumes:
      - pip-cache:/root/.cache/pip        # named volume
      - ./artifacts:/artifacts:ro         # relative to workspace
      - source: /srv/cache                # host path (requires permission)
        target: /cache
        read-only: true
    steps:
      - run: pytest
```

- **Environment isolation**: the container receives only the pipeline variables, never the host variables.
- **Timeout/cancellation**: the process tree of the step is killed *inside* the container (via `/proc`), preserving the container for steps using `if: always()`.
- **Volume security**: named volumes and paths relative to the workspace are always allowed; absolute host paths (e.g. `/var/run/docker.sock`) are denied unless `ORQ_DOCKER_ALLOW_BIND_MOUNTS=true`, optionally restricted by `ORQ_DOCKER_ALLOWED_BIND_PATHS='["/srv/cache"]'`.
- **Limits**: `ORQ_DOCKER_MEMORY_LIMIT` (e.g. `2g`), `ORQ_DOCKER_CPUS`, `ORQ_DOCKER_NETWORK`, pull policy `ORQ_DOCKER_PULL_POLICY` (`always` | `if-not-present` | `never`).
- **Docker-out-of-Docker**: when the orchestrator runs inside a container using the host socket, `ORQ_DOCKER_HOST_WORKSPACES_DIR` specifies where the workspaces are located on the host.

Image requirement: `/bin/sh` and `cut` (Debian, Alpine, Ubuntu...). Distroless images are not supported.

## Webhook Server

```bash
cp projects.example.yml projects.yml      # configure accepted repositories
export GITHUB_WEBHOOK_SECRET=...           # secrets referenced via ${VAR}
orquestrador serve --host 0.0.0.0 --port 8000
```

Configure on GitHub (*Settings → Webhooks*) the URL `https://your-host/webhooks/github`, content type `application/json` and the same secret; on GitLab, `https://your-host/webhooks/gitlab` with the *Secret token*. Accepted events: `push` (branches and tags) and `pull_request` / *Merge Request*.

| Endpoint | Description |
|----------|-----------|
| `POST /webhooks/{github\|gitlab}` | Receives the event, validates the signature and schedules the execution |
| `GET /health` | API status and number of projects |
| `GET /docs` | Interactive OpenAPI documentation |

Responses: `202 queued` (execution scheduled), `200 ignored`/`pong`, `401` invalid signature, `404` repository not configured, `400` invalid payload, `413` body too large, `503` scheduling failure.

Execution flow:

1. The route reads the raw body (with a limit), identifies the project and validates the **HMAC-SHA256 signature** (GitHub, `X-Hub-Signature-256`) or the **token** (GitLab, `X-Gitlab-Token`) in constant time.
2. The event is normalized into a `TriggerEvent` and sent to the `Dispatcher`; the API responds immediately.
3. The `RunService` clones the repository at the exact commit (`git clone` hardened: no prompt, restricted protocols, validated SHA), reads the pipeline from the repository, checks the `on` triggers (globs `*`, `**` and negation `!`) and executes it with the `PipelineRunner`.
4. The result is stored in `<ORQ_DATA_DIR>/runs/<run_id>.json` and the workspace is removed.

Environment configuration (prefix `ORQ_`, see `.env.example`): `ORQ_PROJECTS_FILE`, `ORQ_DATA_DIR`, `ORQ_MAX_PARALLEL_JOBS`, `ORQ_MAX_CONCURRENT_RUNS`, `ORQ_KEEP_WORKSPACES`, `ORQ_MAX_WEBHOOK_BODY_BYTES`, `ORQ_CHECKOUT_TIMEOUT`.

## Execution Queue (Redis + RQ)

By default (`ORQ_DISPATCHER=thread`) the API executes pipelines in a thread pool within the same process, which is practical for development. In production, use the queue:

```bash
export ORQ_DISPATCHER=rq ORQ_REDIS_URL=redis://localhost:6379/0
orquestrador serve                 # receives webhooks and only enqueues (responds 202 immediately)
orquestrador worker                # consumes the queue and executes; run as many as needed
orquestrador worker --burst        # processes what is available and exits
```

```text
GitHub/GitLab ──webhook──▶ API (FastAPI) ──RunRequest JSON──▶ Redis (queue "orquestrador")
                                                                  │
                                          ┌────────────────────────┼────────────────────────┐
                                          ▼                        ▼                        ▼
                                      worker 1                 worker 2                 worker N
                                   RunService → Executor (local | docker) → PipelineRunner
```

- **Decoupling**: the API never executes a pipeline; if Redis goes down, the webhook receives `503` and GitHub/GitLab can retry.
- **Two-level parallelism**: N workers = N simultaneous executions; within each execution, independent jobs run in parallel (`ORQ_MAX_PARALLEL_JOBS`).
- **JSON serialization** (not pickle): the queue is readable and a compromised Redis cannot inject Python objects into the workers. The `run_id` is the RQ job ID (idempotent and traceable).
- **Workers**: `fork` (default on Linux, each execution in a child process) or `simple` (Windows). `ORQ_RUN_TIMEOUT` limits the maximum duration; unexpected failures go to the RQ *failed registry*.
- `GET /health` shows the queue state: `queued`, `started`, `failed` and `workers`.

## Execution History (PostgreSQL)

Each execution is stored with status, duration and logs from each step:

```text
runs ──1:N── job_runs ──1:N── step_runs ──1:N── log_lines
(event, commit,   (status, error,     (status, exit code,   (seq, stdout/stderr,
 status, reason)    duration)           duration, truncated)   text, timestamp)
```

```bash
export ORQ_DATABASE_URL=postgresql+psycopg://orq:password@localhost:5432/orquestrador
orquestrador db upgrade          # apply Alembic migrations
orquestrador db current          # applied revision vs available
orquestrador history --project api --status failure
```

Without `ORQ_DATABASE_URL`, SQLite is used at `<ORQ_DATA_DIR>/orquestrador.db` (great for development).

| Endpoint | Description |
|----------|-----------|
| `GET /api/runs?project=&status=&limit=&offset=` | Paginated executions, newest first |
| `GET /api/runs/{run_id}` | Details with jobs, steps and log count |
| `GET /api/runs/{run_id}/jobs/{job_id}/steps/{n}/logs?after=` | Incremental logs (basis for live streaming) |

Registered lifecycle:

1. **queued** the API registers the execution before enqueueing (if Redis fails, it becomes **error**).
2. **running** the worker marks the start; after checkout, it creates jobs and steps as *pending*.
3. During execution, the `PersistenceObserver` updates jobs/steps and writes logs **in batches** (100 lines or 0.5 s), with a per-step limit (`ORQ_MAX_LOG_LINES_PER_STEP`).
4. **success / failure / cancelled / skipped / error** final outcome with duration and reason.

Decisions: typed SQLAlchemy 2.0 + Alembic (versioned migrations, `render_as_batch` for SQLite); dates always in UTC; `ON DELETE CASCADE` throughout the hierarchy; the repository returns Pydantic DTOs, so API and CLI never manipulate ORM sessions; database failures are isolated and **never** interrupt a pipeline.

## Web Dashboard

With `orquestrador serve` running, access `http://localhost:8000`:

| Page | What it shows |
|--------|--------------|
| `/runs` | Executions with project and status filters; the table automatically updates every 3 s (HTMX) |
| `/runs/{run_id}` | Commit metadata, jobs and steps with status and duration, and **live logs** per step |
| `/projects` | Configured projects and the latest execution for each one (secrets are never displayed) |

Live logs via **WebSocket** (`/ws/runs/{run_id}`): the server periodically queries the database (`ORQ_LIVE_POLL_INTERVAL`, default 0.5 s) and sends only what changed: execution state when something changes (`run`), new lines from each step (`logs`) and `end` when it finishes. The browser reconnects automatically with backoff if the connection drops.

Decisions:

- **Server-side rendering + HTMX** instead of SPA: no frontend build, Jinja2 templates with automatic escaping and HTMX (vendored in `static/`, works without internet) for partial updates.
- **Database-powered WebSocket** instead of Redis pub/sub: API and workers only need to share PostgreSQL; the interval matches the log write batch interval of the `PersistenceObserver`.
- **Browser security**: logs and commit messages enter the DOM only via `textContent`.

## Pipeline Format

```yaml
name: my-project

on:                         # triggers (used by webhooks)
  push:
    branches: [main, "release/*"]
  pull_request:

env:                        # global variables
  PYTHON_VERSION: "3.11"

jobs:
  lint:
    steps:
      - run: ruff check .

  test:
    needs: lint             # dependencies (form a DAG)
    timeout: 600            # job timeout (s)
    env:
      SUITE: unit
    steps:
      - name: tests
        run: pytest
        timeout: 300        # step timeout (s)
      - name: optional coverage
        run: coverage report --fail-under=90
        continue-on-error: true
      - name: cleanup
        if: always()        # runs even after failure
        run: rm -rf .cache

  deploy:
    needs: test
    if: branch == 'main' && event == 'push'
    steps:
      - run: ./deploy.sh
        shell: bash         # bash | sh | python | pwsh | powershell | cmd | "template {0}"
        working-directory: infra
```

### Execution Semantics

- **Steps** run sequentially. If a step fails, the following steps are **skipped**, except those using `if: always()` or `if: failure()`.
- **Jobs** are ordered topologically by `needs`. Jobs without dependencies can run in parallel (`--parallel N`). If a dependency fails or is skipped, the job is skipped (unless `if: always()`).
- `continue-on-error` marks the step/job as failed, but does not propagate the failure.
- Each step receives `stdout`, `stderr`, exit code and duration in the result.

### `if` Expressions

Evaluated by a safe AST-based interpreter (never `eval`).

| Feature | Example |
|---------|---------|
| Variables | `branch`, `tag`, `event`, `commit`, `ref`, `repository`, `actor`, `pipeline`, `job`, `run_id` |
| Environment | `env.DEPLOY == 'true'` |
| Operators | `==`, `!=`, `<`, `in`, `not in`, `and`/`&&`, `or`/`\|\|`, `not`/`!` |
| Functions | `startsWith()`, `endsWith()`, `contains()`, `matches()` (glob) |
| Status | `success()`, `failure()`, `always()`, `cancelled()` |

Without a status function, the expression is implicitly combined with `success()`.

### Injected Variables

`CI=true`, `ORQ_RUN_ID`, `ORQ_PIPELINE`, `ORQ_JOB`, `ORQ_STEP`, `ORQ_EVENT`,
`ORQ_WORKSPACE`, `ORQ_REF`, `ORQ_BRANCH`, `ORQ_TAG`, `ORQ_COMMIT`, `ORQ_REPOSITORY`, `ORQ_ACTOR`,
`ORQ_BASE_BRANCH` and `ORQ_PULL_REQUEST` (in pull/merge requests).

Precedence (highest wins): CLI `--env` > step `env` > job `env` > pipeline `env` > injected variables.

## Architecture (so far)

```text
src/orquestrador/
├── pipeline/          # Pydantic models, YAML parser, condition evaluator
├── execution/         # PipelineRunner, RunContext, results, event observers
├── executors/         # Executor/JobSession, LocalExecutor, DockerExecutor, shells, factory
├── webhooks/          # GitHub/GitLab adapters, TriggerEvent, trigger matching
├── dispatch/          # RunRequest/RunOutcome, RunService, dispatchers (sync, threads, RQ)
├── bootstrap.py       # composition root: builds registry, service and dispatcher
├── api/               # FastAPI: create_app, webhook routes, health and /api/runs
├── db/                # SQLAlchemy: models, repository, observer, listener, Alembic migrations
├── web/               # dashboard: Jinja2/HTMX pages, live-log WebSocket, CSS/JS
├── projects.py        # project registry (projects.yml with ${VAR})
├── scm.py             # secure git checkout
├── config.py          # Settings (pydantic-settings, ORQ_ prefix)
├── console.py         # observer that prints progress to the terminal
└── cli.py             # CLI (Typer): run, validate, serve, worker, history, db, version
```

- **Executor → JobSession**: the executor is a stateless factory; the session stores the state of a job (temporary directory in the `LocalExecutor`, the container in the `DockerExecutor`). This allows parallel jobs with a single executor instance, and switching from subprocess to Docker required no changes to the runner.
- **Observers**: the runner only emits events (`on_step_output`, `on_job_end`...). Console, database, WebSocket and notifications are independent observers.
- **Dispatcher**: the API never executes pipelines in the request; it passes a `RunRequest` (JSON serializable) to a `Dispatcher` — thread pool or Redis + RQ queue. Switching between them in Phase 4 did not change any line of the webhook route or `RunService`.
- **Provider adapters**: GitHub and GitLab implement the same `ProviderAdapter` (repository, verification, event type, parsing), so there is a single generic route.
- **Pipeline in the repository**: like GitHub Actions, the YAML lives in the repository and is read from the exact commit of the event; the server only stores the repository → secret mapping.
- The project itself has a CI pipeline in [.orquestrador.yml](.orquestrador.yml).
